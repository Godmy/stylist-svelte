### 1.1 Адресация и таксономия

Каждая единица кода адресуется путём `<domain>/<cluster>/<joint>/<family>/`. Кластеры — это
ключевые слова TypeScript, развёрнутые в морфологический ящик Цвикки, а компонентный кластер —
это уровни Atomic Design:

| Кластер     | Разрешённые joint’ы (AGENTS.md)                                                                                     | Файлов | Семейств |
| ----------- | ------------------------------------------------------------------------------------------------------------------- | -----: | -------: |
| `data`      | json, jsonl, shader, icon, flag, png, md, yaml                                                                      |    711 |      692 |
| `const`     | value, map, record, preset, array, object                                                                           |    410 |      285 |
| `type`      | alias, record, struct, preset, object, compute                                                                      |    366 |      258 |
| `interface` | behavior, slot, recipe, contract                                                                                    |    998 |      858 |
| `class`     | manager                                                                                                             |    129 |       84 |
| `function`  | script, state, hook, transform, test, async, async-get, async-post, merge, check, count, create, resolve, serialize |    208 |      121 |
| `component` | atom, molecule, organism, template, page                                                                            |   2670 |      690 |

Направление сборки: `data → const → type → interface → class → function → component`.

Найденные нарушения таксономии (единичные, но показательные — их должен ловить линтер, а не человек):

- `input/const/style` — joint `style` не входит в список для `const`;
- `localization/function/format-date-time` — joint `format-date-time` не входит в список для `function`
  (по смыслу это `function/transform/format-date-time`);
- в папках компонентов живёт `state.svelte.ts`, тогда как раздел «Allowed Files» в AGENTS.md его
  не перечисляет (хотя issue его разрешает) — политику стоит синхронизировать.

## 2. Сборка «самостоятельно» — что получилось

Задача из issue: «финальный index.ts нужно подрезать для сборки, часть встроенных репозиториев
загрузится, часть — нет; добиться сборки самостоятельно».

1. Публичные субмодули `src/lib/server`, `src/lib/theme`, `src/lib/svg` клонируются; приватные
   `adr`, `src/lib/wbd`, `src/lib/geo` — нет (`Repository not found`).
2. `yarn install --immutable` — ок (нужен `corepack enable`).
3. `yarn build:site` (сборка песочницы, не пакета) падает **дважды**, и обе причины не связаны с
   корневым `index.ts`:
   - `graph/component/organism/zwicky-scene/index.story.svelte` импортирует
     `$stylist/graph/data/json/step-2-dependencies.json?url`, а файл удалён в `331ad6e85`
     («Move domain component trees out…») и не восстановлен в `9ebb09bbb` («come back»).
     **Это баг в `main`, он ломает сборку и у автора, если у него нет локальной копии файла.**
   - `token/const/object/geo/index.ts` импортирует `MAP_PROVIDER`, `TOKEN_MAP_TYPE`, `TOKEN_PIN` из
     приватного `geo` → публичный домен `token` жёстко зависит от приватного субмодуля.
4. После восстановления JSON из `a94243f8e` и трёх однострочных заглушек для `geo` сборка проходит:
   **3 мин 09 с** (client 1:19, server 2:16), **1685** JS-чанков клиента, 22 МБ immutable-ассетов,
   `.svelte-kit/cloudflare` — 77 МБ / 8074 файла, 73 предупреждения `state_referenced_locally`,
   42 — `css_unused_selector`.

Скрипт, который воспроизводит это без правки отслеживаемых файлов:
[`experiments/prepare-local-build.sh`](../experiments/prepare-local-build.sh) (`--revert` убирает всё,
что он создал).

Почему корневой `index.ts` не мешает песочнице: SvelteKit-маршруты импортируют модули точечно
(`$stylist/<domain>/…`), а stories подгружаются через `import.meta.glob`, поэтому Vite не трогает
`./wbd` и `./geo` из barrel’а. А вот `src/routes/app.svelte` (не маршрут, пример темы) импортирует
`$stylist` целиком — если его когда-нибудь подключить, сборка без приватных субмодулей упадёт.

### 2.1 Риск для npm-пакета (выведен из конфигурации, `svelte-package` не запускался по AGENTS.md)

- `package.json → files` исключает `dist/chat/**`, `dist/commerce/**`, `dist/domain/**`, `dist/geo/**`,
  `dist/management/**`, `dist/marketing/**`, `dist/science/**`, `dist/server/**`, `dist/social/**`
  и все JSON-файлы (`dist/**/*.json`).
- При этом `src/lib/index.ts` содержит `} from './chat'`, `'./commerce'`, `'./domain'`, `'./geo'`,
  `'./management'`, `'./marketing'`, `'./science'`, `'./social'`, `'./wbd'`.
- Значит, `dist/index.js`, собранный из текущего barrel’а, будет ссылаться на папки, которых нет в
  tarball’е → у потребителя `import { Button } from 'stylist-svelte'` упадёт с
  `ERR_MODULE_NOT_FOUND`/ошибкой резолва Vite. Опубликованная `1.0.1` этого избежала только потому,
  что тогда была другая таксономия (`architecture`, `color`, `information`, `interaction`, `media`).
- Не задан `"sideEffects": false` — tree-shaking единого barrel’а на ~2800 строк будет хуже, чем мог бы.

## 3. Оценка архитектуры

### 3.1 Что сделано сильно

1. **Детерминированная адресация.** Путь `<domain>/<cluster>/<joint>/<family>` однозначно
   определяет место любого артефакта. Для ИИ-агентов это огромное преимущество: не нужно «искать,
   куда положить», есть один правильный ответ.
2. **Одна сущность — один файл, автогенерируемые barrel’ы.** Модель конфликтов в git минимальна,
   агентам запрещено руками править barrel’ы, индексатор пересобирает их.
3. **Явный граф направлений** `data → … → component` — фактически слоистая архитектура, которую
   можно проверять статически.
4. **Recipe/slot/behavior/contract (DSIAP)** — интерфейсы компонентов вынесены из `.svelte` и
   доступны без Svelte-компилятора (их можно скармливать ИИ как «API компонента»).
5. **Минимум внешних зависимостей** (`marked`, `shiki`) — свой рендер, свои иконки, свои графики.
   Причём `shiki` нигде не импортируется, а `marked` нужен только `domain/component/organism/markdown-renderer`
   (домен `domain` исключён из пакета) — обе зависимости можно перенести в `devDependencies`.
6. **Песочница сама построена из библиотеки** (`domain/component/page/domain-playground`) —
   dogfooding: любой регресс компонентов сразу виден в собственном UI.
7. **Lazy stories**: `import.meta.glob(..., { eager: false })` — каждая story отдельный чанк.
8. **Манифест** — машинно-читаемое описание всей библиотеки (дерево + 779 дескрипторов со ссылками
   на recipe/state/story/json) — готовая база для RAG/агентов.

## 4. Рекомендации (по приоритету)

### P0 — «чтобы чистый клон собирался и CI был зелёным»

1. Удалить `prettier-plugin-tailwindcss` из `.prettierrc` (Tailwind в проекте не используется) или
   добавить его в `devDependencies`.
2. Вернуть `src/lib/graph/data/json/step-2-dependencies.json` или переписать
   `zwicky-scene/index.story.svelte` на загрузку по `fetch` из `static/` (1.19 МБ JSON не место в
   графе модулей).
3. Разорвать `token → geo`: перенести `MAP_PROVIDER`/`TOKEN_MAP_TYPE`/`TOKEN_PIN` в публичную часть
   (например, `token/const/array/…`) или сделать `token/const/object/geo` частью `geo`.
4. Генерировать **два** корневых barrel’а: `index.ts` (только публичные домены, входит в пакет) и
   `index.private.ts`/`index.full.ts` (с `wbd`, `geo`). Правило: barrel включает только те домены,
   у которых есть `.git`-субмодуль/папка на диске — тогда «подрезка» происходит автоматически.
5. Синхронизировать `package.json → files` с содержимым barrel’а (или исключать домены на уровне
   генератора barrel’а, а не `files`), добавить `"sideEffects": ["**/*.css"]`.

### P1 — «качество, которое ИИ не может испортить молча»

6. **Минимальный тест на каждую семью компонентов**, генерируемый автоматически: рендер с
   дефолтными props без ошибок + snapshot `recipe`-интерфейса. Это 689 тестов, которые пишутся
   скриптом, а не руками.
7. **Визуальный регресс**: прогон всех stories в Playwright × {mobile, tablet, desktop} × {light, dark}
   с сохранением PNG (подробно — в `routes/readme.md`, раздел 5).
8. **Линтер таксономии** (ESLint-правило или скрипт в CI): путь соответствует
   `<domain>/<cluster>/<joint>/<family>`, joint из белого списка, направление импортов
   `data→…→component` не нарушено, публичный домен не импортирует приватный.
9. Типизировать `Story`: `Story<TValues>` с `children?: Snippet<[TValues]>` — уйдут 500+ `any`.
10. Переписать адаптивность компонентов с `@media` на `@container` (или дублировать, как уже
    сделано в `travel-commerce/component/template/cart-page`).

### P2 — «масштабирование»

11. Опубликовать индексатор/аудитор (сейчас Python с Windows-путями) в репозиторий как Node-скрипты
    (`scripts/`), чтобы манифест пересобирался в CI на каждом PR (`git diff --exit-code` на манифест).
12. Разделить манифест: `tree.json` (лёгкий, в SSR) + `descriptors/<domain>.json` (по требованию).
13. Вынести продуктовые домены (`spanish`, `travel-*`, `wbd`, `turtle-*`) в отдельные пакеты/
    субмодули по образцу `wbd` и `geo`; в ядре оставить только переиспользуемое.
14. Объединить дубли (см. `lib/readme.md`, раздел 4) и закрепить «владельца» каждого понятия.
15. MCP-сервер поверх манифеста: `list_domains`, `get_component(path)`, `get_recipe`, `get_story`,
    `screenshot(path, device)` — превращает библиотеку в инструмент для любых агентов.

## 6. Стратегии

1. **«Сначала контур качества, потом объём».** Заморозить добавление новых доменов до зелёного CI,
   автотестов и визуального регресса. Каждый следующий компонент принимается только с story,
   типизированными controls и проходящим скриншот-тестом.
2. **«Манифест как единственный источник правды».** Песочница, barrel’ы, пакет, MCP, скриншот-раннер
   и тесты строятся из манифеста; манифест генерируется в CI. Расхождение диска и манифеста = красный CI.
3. **«Ядро открыто, вертикали — субмодули».** Публичный пакет собирается только из публичных доменов;
   приватные домены подключаются как отдельные пакеты, а не через общий barrel.
4. **«Container-first адаптивность».** Компоненты реагируют на ширину контейнера, страницы/шаблоны —
   на viewport; песочница отображает шаблоны в iframe (см. `routes/readme.md`).
5. **«ИИ как ревьюер визуала».** Скриншоты stories × устройства × темы + JSON-описание (recipe, DOM,
   метрики доступности) отправляются модели, ответ превращается в issue/PR — это и есть «Hive Mind»
   в практическом смысле.
