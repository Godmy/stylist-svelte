# Правила разработки библиотеки stylist-svelte

## Организация рабочего пространства библиотеки (обязательно)

### ADR-001 - Политика организации рабочего пространства и использования библиотеки stylist-svelte (обязательно)

- Библиотека stylist-svelte представляет собой зонтичный репозиторий с публичными и приватными пространствами.
- Проект использует стандартный пакетный менеджер — Yarn 4; `packageManager` в `package.json` задаёт версию. `yarn.lock` — основной lockfile.
- Установку зависимостей и запуск scripts выполняйте через Yarn. Конкретные команды определяются доступным `package.json`.
- Домены, зарегистрированные как Git-подмодули в `.gitmodules` репозитория-владельца, рассматриваются как границы встроенных репозиториев.
- Весь исходный код внутри встроенного репозитория должен соответствовать правилам доменов, кластеров, звеньев, семейств и сборки

### ADR-002 - Политика адресного пространства внутри библиотеки stylist-svelte (обязательно)

- `<domain>/<cluster>/<joint>/<family>` - адрес сущности внутри библиотеки. Группировка репозиториев не добавляет уровень к этому логическому адресу.
- `$stylist/<domain>/<cluster>/<joint>/<family>` - логический абсолютный спецификатор для импорта файлов внутри библиотеки.
- Инфраструктура внутри доменных кластеров использует только абсолютные спецификаторы для импорта.
- Инфраструктура вне доменных кластеров (Node-скрипты, файлы пакетов и конфигураций) может использовать относительные пути.
- Относительные пути импорта используются только внутри автогенерируемых файлов-баррелей `index.ts`.

## Архитектура библиотеки (обязательно)

### ADR-003 - Политика каталожной организации адресного пространства в морфологическом ящике (обязательно)

- Каталоги вида `.../<domain>/...` рассматриваются как предметные домены.
- Содержимое `<domain>` должно соответствовать предметной области и быть кластеризованным в соответствии с ограничением языка внутри каталогов `<cluster>`.
- Каталоги вида `.../<cluster>/...` рассматриваются как строгая типизация на уровне языка TypeScript и Svelte.
- Содержимое `<cluster>` должно соответствовать его названию и находится внутри каталога строго типизированного подходящего звена - `/<joint>/`.
- Каталоги вида `.../<joint>/...` рассматриваются как строгая логическая типизация сущностей:
  -- `interface` - содержит шаблон сборки доменно-специфичных интерфейсов DSIAP и каталоги импортов.
  -- `function` - содержит названия чистых функций согласно функциональной таксономии.
  -- `class` - содержит названия паттерна проектирования, отражающее роль класса.
  -- `component` - содержит названия структурных элементов атомного дизайна.
  -- `test` Содержат наборы тестов Vitest для юнит-тестирования и визуализации.
- Содержимое `<family>` является основным семейством сущности, имена каталогов сущностей пишутся в `kebab-case`.
- Каталоги вида `.../<family>/` рассматриваются как основное семейство сущностей, например `canvas` или `theme`.
- Каталоги вида `.../<family-trait>/` рассматриваются как уточнение основного семейства, например `canvas-axis` или `theme-mode`.
- Каталоги вида `.../<family-trait-trait>/` рассматриваются как более детальное уточнение, например `canvas-axis-x` или `theme-mode-light`.

### ADR-005 - Политика направления сборки (обязательно)

- Сохраняйте основное направление композиции: `data` → `const` → `type` → `interface` → `function` → `class` → `component` → `test`.
- Допускаются обратные зависимости для объявления типизированных констант: `type` → `const` и `interface` → `const`.
- Допускается обратные зависимости для создания суперпозиций функций, которые используют шаблоны проектирования: `class` → `function`.
- Все остальные обратные зависимости запрещены. Не создавайте зависимости, нарушающие это направление, без явного согласия пользователя.
- Внутри `interface/` для DSIAP действует дополнительное одностороннее направление: `behavior` / `slot` → `recipe`

#### ADR-005-01 - DSIAP: шаблон сборки доменно-специфичных интерфейсов (обязательно для `interface/`)

- `behavior` — атомарная поведенческая возможность (например, `BehaviorClickable`, `BehaviorFocusable`).
- `slot` — атомарная поверхность для контента или данных (например, `SlotLabel`, `SlotIcon`).
- `recipe` — композиция интерфейса компонента, собираемая из behaviors, slots и необязательных контрактов с внешними системами.
- Для композиции используйте `theme/type/compute/intersect-all` и оформляйте `recipe` через `ComputeIntersectAll<[...]>`.

#### ADR-005-02 - Политика использования интерфейсов внешних систем (обязательно для `interface/`)

- `contract` — используется при необходимости отдельного соглашения на границе системы или между системами.
- `rest` — используется при необходимости отдельного соглашения для протокола REST.
- `graphql` — используется при необходимости отдельного соглашения для протокола GraphQL.
- Каталоги `contract`, `rest`, `graphql` используется, когда необходимо отдельное соглашение на границе взаимодействия.

### ADR-008 - Политика использования синтаксиса Svelte 5, типизации и реактивности компонентов (обязательно)

- В библиотеке используются плоские компоненты, которые собираются из `recipe`, `state` и при необходимости из других компонентов.
- Компонент импортирует самостоятельные сущности вместо скрытого объявления рядом с разметкой.

#### ADR-008-01 - Политика использования Svelte 5 внутри компонентов (обязательно)

- Основной механизм реактивности — Svelte 5 runes: `$state`, `$derived`, `$effect`.
- Передаваемый контент принимайте через props типа `Snippet` и выводите через `{@render ...}`.
- Именованный контент описывайте отдельными Snippet-props; fallback задавайте явно.
- Используйте `onclick`, `onchange`, `oninput` и другие event-атрибуты вместо `on:click`, `on:change`, `on:input`.
- Типизируйте props в месте `$props()` через импортированный recipe или соответствующий тип.
- Используйте глобальный браузерный `MouseEvent`; не импортируйте его из `svelte/elements`.

#### ADR-008-02 - Политика использования компонентами механизма реактивности и экспорт state-файлы (обязательно)

- Если компонент предполагает наличие реактивного поведения, вся логика этого поведения должна инкапсулироваться внутри файла с названием: `state.svelte.ts`.
- `const state = stateFn(() => props)` - это базовый паттерн вызова state-функции внутри компонента для реактивного чтения актуальных props.
- `$state()` используется как инициализатор переменной. Карточка state-файла содержит пример возврата реактивного значения через getter.
- `state.svelte.ts` - содержит один `export function`, поименованный через `export default <function-name>`, считающийся одной сущностью экспорта.
- Входной параметр описывается как `getProps: () => RecipeComponent`, где `RecipeComponent` — интерфейс соответствующего компонента.
- Расположение файла с одним потребителем: `.../<family>/state.svelte.ts`.
- Расположение файла с несколькими потребителями: `<domain>/<function>/<state>/<family>/state.svelte.ts`.
- Актуальные props внутри state-функции могут читаться через `const props = $derived(getProps())`.
- Вычисляемые на их основе значения описываются через `$derived(...)` или `$derived.by(...)`.

#### ADR-008-03 - Политика демонстрации компонентами своего функционала story-файлы (обязательно)

- Для демонстрации функционала компонента требуется наличие файла контракта story: `.../<family>/index.story.ts`.
- Контракт story `ContractStory` из `html/interface/contract/story`.
- Элементы управления — `SlotStoryControl` из `html/interface/slot/story-control`.
- Описывает компонент, аргументы, элементы управления, предустановки и содержимое `HtmlNode`.
- Типизированное содержимое описывается через `...\interface\recipe\<family>` компонента.
- Для пользовательского рендеринга story при передаче аргументов через props используется `.../<family>/index.story.svelte`.
- Демонстрация должна содержать проверяемый сценарий, а не пустой файл.

## Разработка программного обеспечения и изменение исходного кода (обязательно)

### ADR-009 - Правила изменения исходного кода и согласования изменений (обязательно)

- Сохраняйте согласованность имён файлов и каталогов с моделью `<domain>/<cluster>/<joint>/<family>`.
- Файлы реализации находится непосредственно в `<domain>/<cluster>/<joint>/<family>/`.
- Разрешено изменять реализацию отдельных сущностей `index.ts` имеющих адрес: `<domain>/<cluster>/<joint>/<family>/index.ts`.
- Сохраняйте строгую типизацию сущностей на уровне языка и логической структуры модели.
- Если задача требует структуры, выходящей за пределы `<domain>/<cluster>/<joint>/<family>`, сообщите об архитектурном конфликте.
- Если задача пользователя противоречит архитектурным правилам, явно сообщите о конфликте до начала работы.
- Если тип сущности не соответствует кластеру, перенесите сущность в подходящий кластер либо исправьте форму объявления, если кластер выбран верно.
- Создавайте новый домен только тогда, когда сущность явно не относится ни к одному существующему домену.
- Автоматически генерируемые `index.ts` баррели могут экспортировать множество сущностей.
- Кроме данных и тестов, каждый файл исходного кода должен экспортировать ровно одну сущность.
- По умолчанию помещайте новую сущность в существующий домен, если она естественным образом ему соответствует.
- Изменение реализации и обновление сгенерированных экспортов — отдельные действия.
- Если механизм генерации отсутствует в полученной библиотеке, передайте эту потребность сопровождающему.
- При добавлении, переименовании или переносе сущности укажите, какие экспорты требуют обновления.
- Изменение исходников, обновление генерируемых файлов, проверка, публикация и приёмка имеют отдельные результаты; не заявляйте о невыполненном этапе.
- Новый `<joint>` вводится после согласования на архитектурной сессии.
- При миграции вынесите самостоятельные сущности в семейства, обновите импорты и потребителей, затем передайте обновление агрегаторов предусмотренному механизму.
- Экспорт должен соответствовать кластеру. Доменное название не подменяет название кластера.
- Перед заменой относительного пути убедитесь, что логический спецификатор разрешается в тот же физический файл во всех поддерживаемых окружениях.
- Потребители импортирует сущности по собственному адресу сущности.
- При необходимости зарегистрируйте алиасы пакетов и исходные пути TypeScript. Сохраняйте суффиксы query/hash.
- Локальные переменные внутри функции, поля и приватные детали класса допустимы.
- Одноразовое промежуточное выражение без собственного смысла можно встроить в место использования.
- Несколько самостоятельных сущностей разнесите по отдельным семействам без увеличения глубины адреса.

### ADR-010 - Запрещённые действия (обязательно)

- Запрещено создавать файлы с несколькими экспортируемыми сущностями.
- Запрещено оставлять необъявленные для экспорта декларации `const`, `type`, `interface`, `function`, `class` верхнего уровня.
- Запрещено добавлять под семейством уровни каталогов; уточняйте имя семейства через `family-trait` или `family-trait-trait`.
- Запрещено добавлять вручную файлы реэкспорта или дополнительные промежуточные уровни реэкспорта.
- Запрещено вручную редактировать сгенерированные агрегирующие файлы `index.ts` и `index.full.ts`.
- Запрещено максировать старые имена и псевдонимы ручным реэкспортом с новым именем.
- Запрещено оставлять скрытые Вынесите их в собственные семейства и импортируйте.
- Запрешено создавать в другом домене файл-переадресацию ради удобного импорта.
- Запрещено создавать ручные `export { ... }`, `export * from ...` и псевдонимы старых имён вместо собственной сущности.
- Запрещено из одного кластера импортировать `test` другого кластера.

### ADR-011 - Справочная информация по сущностям и структуре данных (обязательно)

- Во всех каталогах разрешён только один файл `index.ts`.
- В любом каталоге допускается файл `README.md`, документирующий назначение, сущности по звеньям и потоки данных.
- Диаграммы должны размещаться непосредственно в этих README в блоках `mermaid`, а не в отдельных файлах `.mmd`.
- В корне каждого домена, помимо обычной структуры, разрешены файлы `.git`, `LICENSE`.
- `const/value` - содержит одиночный примитив или `Symbol`.
- `const/map` - содержит плоский объект `key: value`, а не вложенные структуры и не одиночный литерал.
- `const/record` - содержит сущности с `Record<...>`
- `const/preset` - содержит полный набор значений для настройки внешнего вида и определения поведения.
- `const/array` - содержит прямой массив токенов с именем `TOKEN*`.
- `const/object` - содержит `json` портируемые сущности.
- `type/object` - содержит переиспользуемый объектный payload со стабильными полями без поведения.
- `type/struct` - используется для более широких структурных композиций и агрегатов.
- `test/unit` - проверяет `data`, `const`, `type`, `interface`, `class`, `function` без рендера компонентов.
- `test/render` - монтирует компоненты или читает их stories. Любой тест, импортирующий `component`, располагается здесь.
- `function/test` - разрешено только для тестов, не импортирующих компоненты. При работе с доменом такие тесты могут переноситься в `test/unit`.

### ADR-012 - Дополнение: Тесты домена

- Кластер `test` может импортировать любой кластер своего домена.
- Тесты, импортирующие `component`, должны находиться в `<domain>/test/render/<family>/`.
- Тесты размещаются по адресу `<domain>/test/<joint>/<family>/index.test.ts` и ничего не экспортируют.
- Тесты не попадают в агрегирующие экспорты и не импортируются рабочим кодом.

### ADR-013 - Дополнение: Процесс добавления и изменения функциональности

1. Определите предметную область и существующий домен.
2. Выберите кластер по языковому типу, звено по логической роли и семейство по предметному смыслу.
3. Проверьте глубину адреса, направление зависимостей и наличие нужного behavior, slot, recipe, типа, функции или класса среди существующих сущностей.
4. Реализуйте сущности по одной на файл. Для компонента оформите recipe, необходимое состояние и демонстрацию.
5. Добавьте или обновите относящиеся к изменению тесты и документацию. Выберите `unit` или `render` по фактическим зависимостям теста.
6. Обновите потребителей при изменении адресов или имён. Укажите, какие генерируемые экспорты требуют обновления.
7. Выполните доступные проверки проекта и сообщите их фактический результат. Если генерация недоступна в полученной библиотеке, передайте потребность сопровождающему.

Этот порядок собирает применение политик выше; он не требует доступа к приватным инструментам рабочего пространства.
