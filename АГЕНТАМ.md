# Правила разработки библиотеки stylist-svelte

Адрес сущности внутри библиотеки — `<domain>/<cluster>/<joint>/<family>`. Физический корень доменов определяется структурой полученного репозитория или пакета. Группировка репозиториев не добавляет уровень к этому логическому адресу.

## Архитектура библиотеки

### ADR-001 - Политика каталожной организации адресного пространства в морфологическом ящике (обязательно)

- Каталоги вида `.../<domain>/...` рассматриваются как предметные домены.
- Содержимое `<domain>` должно соответствовать предметной области и быть кластеризованным в соответствии с ограничением языка внутри каталогов `<cluster>`.
- Каталоги вида `.../<cluster>/...` рассматриваются как строгая типизация на уровне языка TypeScript и Svelte.
- Содержимое `<cluster>` должно соответствовать его названию и находится внутри каталога строго типизированного подходящего звена - `/<joint>/`.
- Каталоги вида `.../<joint>/...` рассматриваются как строгая логическая типизация сущностей:
-- `interface` - содержит шаблон сборки доменно-специфичных интерфейсов DSIAP и каталоги импортов.
-- `function` - содержит названия чистых функций согласно функциональной таксономии.
-- `class` - содержит названия паттерна проектирования, отражающее роль класса.
-- `component` - содержит названия структурных элементов атомного дизайна.
-- `test` Содержат наборы тестов Vitest для юнит-тестирования и визуализации.
- Каталоги вида `.../<family>/` рассматриваются как основное семейство сущностей, например `canvas` или `theme`.
- Каталоги вида `.../<family-trait>/` рассматриваются как уточнение основного семейства, например `canvas-axis` или `theme-mode`.
- Каталоги вида `.../<family-trait-trait>/` рассматриваются как более детальное уточнение, например `canvas-axis-x` или `theme-mode-light`.

### Политика направления сборки (обязательно)

Сохраняйте следующее направление композиции:

- Кластер `test` может импортировать любой кластер своего домена. Ни один другой кластер не может импортировать `test`.
- Кластер `class` может импортировать `function`: класс вправе вызывать функции своего домена. Сохраняйте существующие классы как классы — не переписывайте их в функции исключительно ради соблюдения направления.
- Не создавайте зависимости, нарушающие это направление, без явного согласия пользователя.
- Внутри `interface/` для DSIAP действует дополнительное одностороннее направление:

```
behavior / slot / contract (необязательный)
                  ↓
                recipe
```

Обратные зависимости запрещены.

#### ADR-004 - DSIAP: шаблон сборки доменно-специфичных интерфейсов (обязательно для `.../interface/...`)

Кластер `interface/` следует целевой модели звеньев:

- `behavior` — атомарная поведенческая возможность (например, `BehaviorClickable`, `BehaviorFocusable`).
- `slot` — атомарная поверхность для контента или данных (например, `SlotLabel`, `SlotIcon`).
- `recipe` — композиция интерфейса компонента, собираемая из behaviors, slots и необязательных contracts.

#### ADR-005 - Интеграция с внешними системами (обязательно для `.../interface/...`)

Кластер `interface/` может содержать импортируемую информацию из внешних систем:
- Каталоги `contract`, `rest`, `graphql` могут содержать в себе не обязательный третий этап после `recipe`.
- Он используется только тогда, когда необходимо отдельное соглашение на границе взаимодействия.
- `contract` — используется при необходимости отдельного соглашения на границе системы или между системами.
- `rest` — используется при необходимости отдельного соглашения для протокола REST.
- `graphql` — используется при необходимости отдельного соглашения для протокола GraphQL.

### Политика подключения и встраивания репозиториев доменов-подмодулей (обязательно)

- Домены, зарегистрированные как Git-подмодули в `.gitmodules` репозитория-владельца, рассматриваются как границы встроенных репозиториев.
- В корне каждого домена, помимо обычной структуры, разрешены файлы `.git`, `LICENSE` и `README.md`.
- Весь исходный код внутри встроенного репозитория должен соответствовать правилам доменов, кластеров, звеньев, семейств и сборки

### ADR-005 - Политика структуры файлов и именования (обязательно)

- Во всех каталогах разрешён только один файл `index.ts`.
- В любом каталоге допускается файл `README.md`, документирующий назначение, сущности по звеньям и потоки данных.
- Диаграммы должны размещаться непосредственно в этих README в блоках `mermaid`, а не в отдельных файлах `.mmd`.

### Правила изменения исходного кода (обязательно)

- Каждый файл исходного кода должен экспортировать ровно одну сущность.
- Сохраняйте строгую типизацию сущностей на уровне языка и логической структуры.
- Не создавайте файлы с несколькими экспортируемыми сущностями.
- Не оставляйте необъявленные для экспорта декларации верхнего уровня.
- По умолчанию помещайте новую сущность в существующий домен, если она естественным образом ему соответствует.
- Сохраняйте согласованность имён файлов и каталогов с моделью `<domain>/<cluster>/<joint>/<family>`.

### Политика логических импортов (обязательно)

- В написанном вручную исходном коде доменов библиотеки используйте логические абсолютные спецификаторы модулей для импортов и реэкспортов, включая stories, тесты, динамические импорты с литеральными путями и типы `import()`. Это правило распространяется и на зависимости внутри одной папки, например `./index.svelte` и `./state.svelte`.
- В исходниках общих доменов используйте настроенный логический алиас в формате `$stylist/<domain>/<cluster>/<joint>/<family>`. При необходимости сохраняйте явно указанные имена файлов и расширения, например `$stylist/button/component/atom/button/index.svelte`.
- При использовании установленной библиотеки импортируйте сущности через подпути пакета `stylist-svelte/<domain>/...`. Алиас `$stylist` требует настройки в проекте и не является именем npm-пакета.
- Перед заменой относительного пути убедитесь, что логический спецификатор разрешается в тот же физический файл во всех поддерживаемых окружениях. При необходимости зарегистрируйте алиасы пакетов и исходные пути TypeScript. Сохраняйте суффиксы query/hash.
- Сгенерированные агрегирующие файлы экспорта остаются под управлением генератора и могут использовать относительные реэкспорты. Не редактируйте их вручную ради соблюдения этой политики. Инфраструктура вне доменных кластеров (Node-скрипты, файлы пакетов и конфигураций) может использовать относительные пути.
- Пути файловой системы, URL ресурсов и вычисляемые пути времени выполнения не являются спецификаторами модулей. Не переписывайте их механически. Если у зависимости нет поддерживаемого логического адреса, сохраните работающий относительный импорт и сообщите об исключении.

### ADR-003 - Политика использования компонентами реактивности (обязательно)

- Если компонент предполагает наличие реактивного поведения, вся логика этого поведения должна инкапсулироваться внутри файла с названием: `state.svelte.ts`.
- `state.svelte.ts` файлы должны содержать один `export function` и выполняться он должен через `export default <function-name>`.
- Расположение файла с одним потребителем: `.../<family>/state.svelte.ts`.
- Расположение файла с несколькими потребителями: `<domain>/<function>/<state>/state.svelte.ts`.

### ADR-004 - Политика демонстрации компонентами своего функционала (обязательно)

- Для демонстрации функционала компонента требуется наличие файла контракта story: `.../<family>/index.story.ts`.
- Контракт story `ContractStory` из `html/interface/contract/story`.
- Элементы управления — `SlotStoryControl` из `html/interface/slot/story-control`.
- Описывает компонент, аргументы, элементы управления, предустановки и содержимое `HtmlNode`.
- Типизированное содержимое описывается через `...\interface\recipe\<family>` компонента.
- Для пользовательского рендеринга story при передаче аргументов через props используется `.../<family>/index.story.svelte`.

## Добавление и изменение функциональности

### Правила согласования изменений (обязательно)

- Если задача требует структуры, выходящей за пределы `<domain>/<cluster>/<joint>/<family>`, сначала сообщите об архитектурном конфликте и только затем предложите решение.
- Создавайте новый домен только тогда, когда сущность явно не относится ни к одному существующему домену.
- Создавайте новый кластер только через новую запись ADR (кластер `test` был добавлен через `adr/folder/cluster/002`).
- Создавайте новое звено только после достижения консенсуса на архитектурной сессии. Доменно-специфичные названия должны размещаться на уровне `family`, а не `joint`.

### Размещение тестов

- Тесты, импортирующие `component`, должны находиться в `<domain>/test/render/<family>/`. Звено `function/test` по-прежнему разрешено только для тестов, не импортирующих компоненты.

### Экспорты и сгенерированные файлы

- Не добавляйте вручную файлы реэкспорта или дополнительные промежуточные уровни реэкспорта.
- Не редактируйте вручную сгенерированные агрегирующие файлы `index.ts` и `index.full.ts`. Файлы реализации отдельных сущностей с именем `index.ts` являются исходным кодом и могут изменяться по правилам выше.
- Изменение реализации и обновление сгенерированных экспортов — отдельные действия. При добавлении, переименовании или переносе сущности укажите, какие экспорты требуют обновления.
- Если механизм генерации отсутствует в полученной библиотеке, передайте эту потребность сопровождающему. Для изменения исходников не требуется получать доступ к приватным инструментам.
- Если задача пользователя противоречит архитектурным правилам, явно сообщите о конфликте до начала работы.

### Дополнение: соответствие языкового типа и кластера

- Экспорт должен соответствовать кластеру. Доменное название не подменяет название кластера.
- Если тип сущности не соответствует кластеру, перенесите сущность в подходящий кластер либо исправьте форму объявления, если кластер выбран верно.
- Набор звеньев фиксирован архитектурой; предметные названия размещаются на уровне семейства.

Источники: [folder/cluster/001](adr/folder/cluster/001/index.yaml), [folder/joint/001](adr/folder/joint/001/index.yaml).

### Дополнение: Константы и структуры данных

- `const/map` содержит плоский объект `key: value`, а не вложенные структуры и не одиночный литерал.
- Значения `const/map` должны быть JSON-переносимыми; `Symbol` в них запрещён.
- `const/struct` упразднён. Сущности с `Record<...>` переносите в `const/record`, плоские соответствия — в `const/map`.
- В ADR также описаны `const/manifest` как объект-манифест, `const/single` как одиночный примитив или `Symbol`, `const/enum` как прямой массив токенов с именем `TOKEN*`. Их соответствие текущим `value`, `array`, `object`, `preset` ещё требует решения; новые сущности не размещайте в исторических звеньях автоматически.

Основание: [folder/joint/002](adr/folder/joint/002/index.yaml), [005](adr/folder/joint/005/index.yaml), [006](adr/folder/joint/006/index.yaml), [007](adr/folder/joint/007/index.yaml), [008](adr/folder/joint/008/index.yaml), [009](adr/folder/joint/009/index.yaml), [010](adr/folder/joint/010/index.yaml), [011](adr/folder/joint/011/index.yaml), [012](adr/folder/joint/012/index.yaml), [013](adr/folder/joint/013/index.yaml), [014](adr/folder/joint/014/index.yaml), [015](adr/folder/joint/015/index.yaml).

### Дополнение: Объектные типы

- `type/object` содержит переиспользуемый объектный payload со стабильными полями без поведения.
- `type/struct` используется для более широких структурных композиций и агрегатов.
- Файл в `type/object` экспортирует ровно один `type`; интерфейсы, классы, константы, функции и компоненты в этом звене не размещаются.

Основание: [folder/joint/017](adr/folder/joint/017/index.yaml).

### Дополнение: сборка recipe и поведенческие интерфейсы

- Новые поведенческие интерфейсы имеют префикс `Behavior` и располагаются в `interface/behavior`. Старое `interface/role` и префикс `Role` считаются переходным наследием.
- Recipe импортирует `StructIntersectAll` из `architecture/type/struct/intersect-all` через поддерживаемый логический адрес и расширяет `StructIntersectAll<[...]>`.

Источники: [folder/joint/003](adr/folder/joint/003/index.yaml), [004](adr/folder/joint/004/index.yaml), [016](adr/folder/joint/016/index.yaml).

### Дополнение: Семейства, имена и глубина адреса

- `<family>` — основное семейство сущности, например `canvas` или `theme`.
- Уточнение семейства записывается через дефис: `canvas-axis`, `theme-mode`, `canvas-axis-x`, `theme-mode-light`.
- Имена каталогов сущностей пишутся в `kebab-case`.
- Не добавляйте суффиксы `-type` и `-interface` только ради обозначения языкового типа: его уже задаёт кластер.
- Файл реализации находится непосредственно в `<domain>/<cluster>/<joint>/<family>/`. Не добавляйте под семейством уровни каталогов; уточняйте имя семейства.

Основание: [folder/family/007](adr/folder/family/007/index.yaml), раздел naming в [file/index/ts/code/002](adr/file/index/ts/code/002/index.yaml). Противоречащие глубине старые примеры вложенных подпапок не используются как образец новой структуры.

### Дополнение: именование файлов и устранение legacy-структуры

- Имя сущности задаёт каталог семейства. Не создавайте соседние `theme.ts`, `container-props.ts` и аналогичные файлы самостоятельных сущностей.
- Сущности документируются с помощью JSDoc.
- Базовый список имён в ADR не учитывает все новые форматы текущего документа; его применение к `state.svelte.ts`, `index.story.ts` и данным требует согласования.

Источники: [file/001](adr/file/001/index.yaml), [file/index/ts/name/001](adr/file/index/ts/name/001/index.yaml), [file/index/ts/legacy/001](adr/file/index/ts/legacy/001/index.yaml).

### Дополнение: Реализация TypeScript-сущности

- Файл реализации `index.ts` определяет ровно одну собственную экспортируемую сущность; пустой файл или файл без экспорта не является корректной сущностью.
- Несколько самостоятельных сущностей разнесите по отдельным семействам без увеличения глубины адреса.
- Не оставляйте скрытые самостоятельные `const`, `type`, `interface`, `function`, `class` верхнего уровня. Вынесите их в собственные семейства и импортируйте.
- Локальные переменные внутри функции, поля и приватные детали класса допустимы. Одноразовое промежуточное выражение без собственного смысла можно встроить в место использования.
- Запрет нескольких экспортируемых сущностей не распространяется на сгенерированные агрегаторы, тесты без экспортов и специальный экспорт одной state-функции под двумя формами.

Основание: [file/index/ts/code/001](adr/file/index/ts/code/001/index.yaml), [002](adr/file/index/ts/code/002/index.yaml), [004](adr/file/index/ts/code/004/index.yaml).

### Дополнение: собственная сущность и псевдонимы экспорта

- Не создавайте в другом домене файл-переадресацию ради удобного импорта. Потребитель импортирует сущность по её собственному адресу.
- Не создавайте ручные `export { ... }`, `export * from ...` и псевдонимы старых имён вместо собственной сущности. Переключайте потребителей на основной адрес и имя.

### Дополнение: Компонент как представление

- Переиспользуемые константы, типы, интерфейсы и функции выносите из `<script>` компонента в соответствующие кластеры.
- Компонент импортирует самостоятельные сущности вместо скрытого объявления рядом с разметкой.
- Привязка props и вызов state-функции остаются частью сборки представления. ADR допускают локальные обработчики событий, использующие локальное состояние; они не должны становиться вторым местом хранения самостоятельной реактивной логики.

### Дополнение: механизм реактивности и экспорт state-функции

- Основной механизм реактивности — Svelte 5 runes: `$state`, `$derived`, `$effect`.
- Именованный `export function` и `export default` той же state-функции считаются одной сущностью с двумя формами экспорта, а не двумя самостоятельными сущностями.
- Базовый паттерн вызова state-функции из ADR — `const state = stateFn(props)`.
- `$state()` используется как инициализатор переменной. Карточка state-файла содержит пример возврата реактивного значения через getter.

### Дополнение: Синтаксис Svelte 5 и типизация

- Передаваемый контент принимайте через props типа `Snippet` и выводите через `{@render ...}`. Именованный контент описывайте отдельными Snippet-props; fallback задавайте явно.
- Используйте `onclick`, `onchange`, `oninput` и другие event-атрибуты вместо `on:click`, `on:change`, `on:input`.
- Типизируйте props в месте `$props()` через импортированный recipe или соответствующий тип.
- Для `HTMLAttributes` указывайте конкретный тип HTML-элемента.
- Типизируйте ключи индексирования объектов; не скрывайте неопределённость произвольным строковым ключом.
- Используйте глобальный браузерный `MouseEvent`; не импортируйте его из `svelte/elements`.

### Дополнение: Тесты домена

- Тесты размещаются по адресу `<domain>/test/<joint>/<family>/index.test.ts` и ничего не экспортируют.
- `unit` проверяет `data`, `const`, `type`, `interface`, `class`, `function` без рендера компонентов.
- `render` монтирует компоненты или читает их stories. Любой тест, импортирующий `component`, располагается здесь.
- Тесты не попадают в агрегирующие экспорты и не импортируются рабочим кодом.
- Существующий `function/test` допустим только без импорта компонентов; при работе с доменом такие тесты могут переноситься в `test/unit`.

Основание: [folder/cluster/002](adr/folder/cluster/002/index.yaml).

## Политика организации рабочего пространства с использованием библиотеки stylist-svelte (обязательно)

- Проект использует стандартный пакетный менеджер — Yarn 4; `packageManager` в `package.json` задаёт версию.
- `yarn.lock` — основной lockfile. Не добавляйте lockfile другого менеджера без отдельного решения.
- Установку зависимостей и запуск scripts выполняйте через Yarn. Конкретные команды определяются доступным `package.json`.
- Изменение исходников, обновление генерируемых файлов, проверка, публикация и приёмка имеют отдельные результаты; не заявляйте о невыполненном этапе.

## Политика рефакторинга и изменения состава файлов библиотеки (обязательно)

- Если задача требует выхода за `<domain>/<cluster>/<joint>/<family>`, сначала сообщите об архитектурном конфликте и предложите решение.
- Новый `<joint>` вводится после согласования на архитектурной сессии.
- Старые имена и псевдонимы не сохраняйте как ручные реэкспорты ради маскировки незавершённого переноса.
- При миграции вынесите самостоятельные сущности в семейства, обновите импорты и потребителей, затем передайте обновление агрегаторов предусмотренному механизму.


### Дополнение: Процесс добавления и изменения функциональности

1. Определите предметную область и существующий домен.
2. Выберите кластер по языковому типу, звено по логической роли и семейство по предметному смыслу.
3. Проверьте глубину адреса, направление зависимостей и наличие нужного behavior, slot, recipe, типа или функции среди существующих сущностей.
4. Реализуйте сущности по одной на файл. Для компонента оформите recipe, необходимое состояние и демонстрацию.
5. Добавьте или обновите относящиеся к изменению тесты и документацию. Выберите `unit` или `render` по фактическим зависимостям теста.
6. Обновите потребителей при изменении адресов или имён. Укажите, какие генерируемые экспорты требуют обновления.
7. Выполните доступные проверки проекта и сообщите их фактический результат. Если генерация недоступна в полученной библиотеке, передайте потребность сопровождающему.
